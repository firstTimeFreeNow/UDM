# アフェティリアハード追加便 Web アプリ設計（たたき台）

実装した内容と残る本番接続作業は [実装状況](afetiria-extra-implementation.md) を参照。
以下は検討経緯を含む設計案であり、すべてを未実装として扱わない。

## 合意した要件

- UDM の Next.js 基盤を使い、サービス名に即した専用ルートで運用する。
- UDM トップや装備プランナーに入口を並べず、ナビゲーションも独立させる。
- 参加者は共通リンクと共通 ID・パスワードで利用し、個別アカウント登録は行わない。
- 管理者は Google ログインを利用し、開催確定やメンバー設定を管理する。
- メンバーの追加と必須メンバーかどうかの設定は、管理者画面からのみ行う。
- ○が9人以上の日時は「人数調整」とし、開催候補一覧から外す。
- 開催日時の確定後も、参加者は回答を変更できる。
- 手動追加した候補も、翌週の同じ曜日・時刻へ引き継ぐ。
- 未確定のまま週が終了した場合は未開催として自動更新する。
- スプレッドシートをデータの正本とし、Web版とシートのどちらの変更も同じデータへ反映する。
- 同じブラウザーでは認証状態を保持し、次回は自動復元する。
- 前回選択したメンバー ID を localStorage に保存し、次回自動選択する。
- サイトデータの削除などで名前の選択が失われた場合は、再選択する。
- 通常のキャッシュ削除やスーパーリロードで名前が消えることは要件としない。
- 個人別リンクによる本人確認は行わず、共通アカウントの参加者は他の名前も選択できる。
- 無料プラン内とし、課金設定を前提にしない。
- 共有 URL 短縮は UDM 共通機能を利用する。管理画面は共有の初期対象外とする。

名前と ID を分けた保存方法、および以下の具体的な構成・データ構造は設計案。

## 画面と構成案

正式なベースパスは `/UDM/afetiria-extra/` を候補とする。
開催状況、`answer/`、`history/`、`admin/` を用意する。
共通リンクは現在の対象週を表示する。

画面配信は GitHub Pages、認証は Firebase Authentication、データの正本は既存スプレッドシートとする。
Apps Script を、認証・権限検証・業務ルール・シート入出力を担うバックエンドの候補とする。
以前の Firestore へ回答を移行する案は、この構成で置き換える。回答の二重保存・双方向DB同期は行わない。
参加者共通アカウントは Firebase のメール・パスワード認証を利用する案。
メール形式のアカウント識別子をどう共通 ID の入力に対応させるかは未確定。
参加者各自のメールアドレス・本名・Google アカウントは収集しない。
共通アカウント用の識別子や管理者情報、パスワードを公開コードに固定しない。

Next.js の共有ルートレイアウトを見直し、装備プランナーのヘッダー・フッターを継承させない。
画面の枠組みは公開されるが、キャラクター名・回答・履歴は認証後に取得する。
認証状態の判定完了前に名前一覧を描画・取得しない。

## 権限案

| 利用者 | 許可 |
| --- | --- |
| 未認証 | ログイン画面、公開短縮リンクの解決のみ |
| 許可済み参加者共通アカウント | 対象サービスのメンバー表示・回答・開催状況・履歴閲覧 |
| 許可済み管理者 | 対象サービスの設定・メンバー・開催確定・締め処理 |

単に Firebase にログインできただけでは参加者や管理者として認めない。
役割とサービスへのアクセス許可をサーバー側の保護された情報で管理する。
バックエンドで認証トークン・権限・受付状態・更新可能項目・入力値を検証する。
シートの直接編集はGoogle側の共有・保護設定で制御する。アプリの権限だけでは直接編集を制限できない。
管理ルートが知られていないことを権限の根拠にしない。
共通ログインでは誰が操作したかを個人単位で特定できない。

## シート上の保存データ案

| データ | 内容 |
| --- | --- |
| 設定・メンバー | ランダムなメンバー ID、ゲーム内表示名、有効状態、必須条件 |
| 設定・メンバーの設定欄 | 対象週、候補時間帯、刻み、最低開催人数、更新猶予 |
| 開催日程・管理用メタデータ | 週 ID、受付状態、開催確定日時、締め状態 |
| （管理者用）回答管理 | 現行の回答正本。週・メンバー ID・日時との対応をバックエンドで解決 |
| 開催履歴 | 終了した開催・未開催と回答のスナップショット |
| バックエンドの保護された設定 | 共通アカウント・管理者のサービス別権限。参加者向けシート・APIから取得不可 |

名前はメンバー対応表に集約し、回答ごとに重複保存しない。
前回選択の保存は名前文字列ではなくメンバー ID とし、表示名は認証後に対応表から取得する。
メンバーが無効になった場合は保存済み ID を自動選択せず、再選択を促す。
ID と対応表を照合できるので、ID 化を匿名化とは扱わない。
実際のメンバー一覧、認証情報、UID を設計資料・公開コード・ビルド成果物に含めない。
履歴の保存期間と削除方法は未確定。

## 回答と週の更新

回答は週とメンバー単位で保存し、未回答と × を区別する。
複数端末からの更新競合の扱いは詳細設計で決める。
現行数式では、有効な参加対象の ○ だけを開催人数に数え、必須メンバー全員の ○ を必要とする。
△は参考表示とし、最低開催人数にも必須条件の達成にも加算しない。
開催可能な候補は ○人数の降順、日付の昇順、時刻の昇順に並べる。
開催確定後も参加者の回答を受け付ける。条件を外れた場合の管理者への案内は設計案として扱う。
判定表、例外、確認根拠は [業務ルール](afetiria-extra-business-rules.md) を参照する。

開催日時が確定している週は、開催2時間後以降の定期処理で履歴保存と週更新を行う。
未確定のまま週が終わった場合は、未開催として更新することが今回の確定要件。
未開催の判定時刻は、対象週の翌月曜0時（日本時間）以降の定期処理とする案。
確定済みの開催が週境界をまたぐ場合は、開催2時間後の期限を優先する案。
手動追加候補を含む候補構成を翌週へ引き継ぐことも確定した。

スプレッドシート上の既存処理とWeb版は、同一の保存・集計・週更新処理を共用する。
トリガーはシート側の1系統にまとめ、Web版専用の週更新処理を並行稼働させない。
ロック・リトライ・履歴の重複防止は設計するが、Sheetsの複数読み書きをDBトランザクションとは扱わない。
詳しくは [シート連動設計](afetiria-extra-sheet-backend-design.md) を参照する。

## 実装前に詰める項目

1. Apps Script 本体・回答 HTML・候補管理 HTML・マニフェスト・トリガー一覧は確認済み。実行間隔の詳細と実行ログは未確認。
2. 候補の翌週継承と未開催時の自動更新は確定。延期・取消・週境界と複数週未実行時の処理を具体化する。
3. 過去データの保持期間と、共通パスワード変更時の既存ログインの失効方針。
4. アカウント識別子・初回管理者設定・APIのトークン検証と、シート共有権限の確認。
5. GitHub PagesからApps Script APIを呼ぶ通信方式・CORS・認証・無料枠内の実行回数を実証する。
6. UDM 共通短縮 URL の管理画面・権限・パスの許可範囲。
