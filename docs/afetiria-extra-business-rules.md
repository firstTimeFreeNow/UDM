## 今回確定した追加・継続要件

- メンバー追加と必須フラグ変更は、管理者画面でのみ実行する。
- ○が9人以上の日時は、現行と同じく開催候補一覧から除外する。
- 開催確定後も参加者は回答を変更できる。
- 一般参加者はメンバー名を選ぶだけであり、メンバー作成・必須設定・権限編集はできない。

- 未確定のまま週が終わった場合は未開催として自動更新する。これは現行からの変更。

## 現行の人数集計と開催判定

確認元は「日程調整」O7:R41 の35行。
集計対象は、名前が空欄でなく、参加対象フラグが TRUE のメンバーに限定される。
参加対象外のメンバーは人数と必須判定の両方から除外される。

- ○人数: 集計対象のうち、当該日時の回答が ○ の人数。
- △人数: 集計対象のうち、当該日時の回答が △ の人数。参考表示であり開催人数には含めない。
- 必須達成: 集計対象の必須メンバー全員が当該日時に ○ と回答していること。
- 必須メンバーの △・×・未回答は、いずれも必須未達となる。
- 対象の必須メンバーが0人の場合、数式上は必須達成となる。
- 未回答は × と別の回答状態として保存するが、どちらも人数に加算しない。

判定は以下の上から順に評価する。現在の最低人数は6人、上限は数式で8人。

| 条件 | 判定 | 開催候補に掲載 |
| --- | --- | --- |
| 必須条件を満たさない | 必須未達 | しない |
| 必須達成かつ○人数が最低人数未満 | 人数不足 | しない |
| 必須達成かつ○人数が9人以上 | 人数調整 | しない |
| 必須達成かつ○人数が最低人数以上8人以下 | 開催可能 | する |

上限8人をWeb版では設定値として持つかは未確定。初期値として現行の8人を提案する。
最低人数と上限の大小関係を検証し、矛盾した設定は保存しない。

## 候補の順位と日時選択

確認元は「開催日程」A9 の FILTER / SORT 式、J9 の候補生成式、B3 の入力規則。
「開催可能」の日時だけを次の順序で並べる。

1. ○人数が多い順。
2. ○人数が同じ場合は日付が早い順。
3. 同じ日付の場合は時刻が早い順。

△人数と設定の「基準時間への近さ」は、この数式では順位に使っていない。
現行のフィルター式には現在時刻との比較がなく、経過済み日時も条件次第で掲載される。
候補がない場合は「開催可能な候補なし」と表示する。
管理者の開催日時選択肢は「開催可能」の候補から生成されている。
Web版でも確定時点で選択した日時の開催条件を再検証する案とする。

## 候補日時の生成

現行の設定値は、月曜から日曜の1週間、20:30〜22:30、30分刻み、基準時間21:30。
「日程調整」A7:B41 は7日×5時刻の35枠になっている。
日付は週開始設定を参照するが、読めた各行の時刻は TIME の定数式。
提供されたスクリプトには開始・終了・刻み設定から全枠を再生成する処理はない。
候補の追加は対象週内かつ30分単位で許可し、設定の開始・終了時間帯は検証していない。

Web版では設定から候補枠を生成する案。時刻変更により保存済み回答の対象枠が変わる操作は、
無条件に回答を削除せず、適用対象週と既存回答の扱いを明示する。
過去日時の候補を隠すかは現行と差が生じるため、別途確定する。

## 管理者のメンバー操作

メンバー追加・必須変更を管理者専用にすることは確定要件。
以下は実装上の提案であり、既存シートの実動作と区別する。

- メンバーはランダムな ID で管理し、表示名の変更で回答の紐づけを変えない。
- 追加時の初期値は「参加対象・必須ではない」、回答は未回答とする案。
- 重複する表示名は回答時の取り違えを避けるため保存前に検証する。
- 参加対象から外す操作は無効化で実現し、過去の回答を連鎖削除しない。
- 必須・参加対象の変更は、現在の対象週の候補集計に反映する案。
- 終了済みの履歴には当時の判定条件を残し、現在の設定変更で書き換えない。
- 必須変更後に確定日時が条件を満たさなくなった場合は、再確認が必要なことを表示する案。
- 参加者が members や settings を直接更新しようとしても拒否する。

## 開催確定後の変更

確定後も参加者の回答変更を受け付けることは今回の確定要件。
以下は、その要件に対する整合性の設計案。

- 受付中 → 開催確定の移行だけでは回答を締め切らない。
- 保存された回答に基づき、人数・必須達成・候補一覧を再集計する。
- 確定日時が候補外になっても、自動的に別日時へ変更・取消しをしない。
- 確定日時を保持したまま「開催条件の再確認が必要」と表示し、管理者が判断する。
- 開催日時の変更は管理者に限定し、次の更新期限も新しい確定日時から計算する。
- 締め処理と同時の回答保存は、週の受付状態を使って整合性を守る。
- 終了週を締めた後の通常回答変更は拒否し、管理者修正の要否は別途確定する。

## 提供された Apps Script 本体から確認した仕様

### 回答保存

- 回答の正本は「（管理者用）回答管理」。旧「回答データ」を読む補助関数は残るが、現行の保存と履歴は管理用の回答表を利用している。
- 週 ID・有効メンバー・現在存在する候補日時を保存時に検証する。
- ○・△・×・空文字だけを許可し、空文字への変更で未回答に戻せる。
- 変更対象だけを保存する。同じリクエストで同じ候補の重複は拒否し、変更なしは成功として扱う。
- 他のメンバーや変更対象外の候補の回答は保持する。
- 開催日時・開催済みかどうかによる保存拒否はない。現在週と候補の一致が保存の主条件。
- DocumentLock で保存・候補変更・週更新を直列化し、取得できなければ保存はエラーになる。
- 閲覧用キャッシュは90秒で、保存・候補変更などで破棄する。キャッシュは回答の正本にしない。

### 候補の追加・削除

- 現行の物理上限はメンバー12枠・候補54枠。これはシート構造の制約で、Web版に同じ制限を採用するかは別途決める。
- 対象週内の日付、30分単位の時刻、日時の重複なしを検証して空き行に追加する。
- 時刻は00:00〜23:30を許可し、現行設定の20:30〜22:30の外にも追加できる。
- 1件でも ○・△・× の回答がある候補は削除できない。未回答だけなら削除できる。
- 候補管理の公開関数に管理者認証の判定は書かれていない。現行の利用権限は実際の共有・実行環境に依存する。
- Web版ではメンバー管理に加え、候補の追加・削除も管理者限定とする案。

### 開催確定と5分間隔の更新

- 「開催日程」B3 に日時が入っていることを確定として扱う。独立した確定状態セルは使わない。
- `installRolloverTrigger` は同じ関数の既存トリガーを削除し、`checkScheduleRollover` の5分間隔トリガーを作成する。
- 提供画像では、時間ベースの `checkScheduleRollover` トリガーが1件登録されている。
- 画像の一覧では実行間隔を確認できないため、5分間隔はソースの設定関数から分かる意図として扱う。
- 未完了処理の再開でなければ、選択日時が Date 型であり現在の候補に存在することを検証する。
- 選択日時から120分経過していなければ何もしない。日時未確定・存在しない候補でも週を進めない。
- このタイミングで開催可能かの再集計は行わない。回答変更で条件未達になっても、候補自体が残っていれば更新対象になる。
- 対象週をキーに既存履歴を探し、なければ候補・メンバー設定・有効メンバーの回答・確定日時を保存する。
- 当該週の履歴を作った後、未完了の週 ID を DocumentProperties に記録する。
- 次週は処理実行日の週ではなく、アーカイブする週の開始日＋7日とする。
- 候補の日付は7日進め、時刻と手動追加候補の構成は引き継ぐ。週開始日を参照する数式は保持する。
- 回答表を全件未回答に戻し、週開始日を更新し、確定日時を空にする。新規の標準枠生成ではない。
- 履歴の既存確認と未完了マーカーにより再開・二重繰り越しの防止を意図しているが、複数書き込みはトランザクションではない。
- 中断位置によって再開状態の検証が必要。Web版はこの手順をそのまま複製せず、週と履歴の原子的な状態更新を設計する。
- 取消・延期・未開催週を明示的に処理する関数は、このファイルにはない。

### 設定の正本に関する差異

- シートの候補一覧式は最低人数の設定セルを使うが、回答画面へ返す判定は `AF.minParticipants = 6` を使う。
- 人数上限はスクリプトで8、更新猶予は120分の定数で、設定セルを読み取っていない。
- 現在は設定値が一致しているが、設定を変更すると画面間で判定がずれる可能性がある。
- Web版では最低人数・上限・更新猶予の正本を一つにし、画面・保存検証・定期処理で共有する案。

## 提供された AnswerDialog HTML から確認した仕様

### 名前と表示

- 有効メンバーを選択肢にし、必須のメンバーは名前に「（必須）」を付ける。
- 現行は選択中の名前を JavaScript の変数にのみ保持する。ダイアログを開き直した後の保持はない。
- 再取得時は同じ画面内の前回選択を優先し、見つからなければ一覧の先頭を自動選択する。
- 日付は週開始から7日分のタブに分け、各日の候補時刻を昇順で並べる。
- 各候補に、取得時点の参加可能人数と判定を表示する。
- 下書き変更では人数と判定は再計算されないため、保存前の選択と表示の集計時点は異なる。
- 候補のない日とメンバーのない場合は、それぞれ説明を表示する。

### 入力・下書き・保存

- ○・△・× をクリックして選択し、選択中の同じボタンをもう一度押すと未回答に戻す。
- 「この曜日はすべて×」は、表示中の曜日の全候補を下書きで × にする操作。
- 曜日を切り替えても下書きは保持する。メンバーを変える場合は未保存変更の破棄を確認する。
- 「回答を保存」まではサーバーへ送信しない。変更を元の値へ戻した候補は差分から除外する。
- 保存ボタンには未保存件数を表示し、差分がなければ保存できない。
- 保存中は候補ボタン・曜日タブ・一括×を無効化し、重複保存を抑止する。
- 保存成功時は再取得せずダイアログを閉じる。保存失敗時は下書きを保持して再操作できる。
- 再読み込みは未保存変更の破棄を確認し、サーバーの強制取得を行う。
- ページ離脱時は未保存変更があれば beforeunload による確認を要求する。
- 未保存下書き自体を localStorage などに保存する処理はない。

### Web版で引き継ぐ内容と変更案

入力・曜日切り替え・当日全件×・差分保存・未保存確認は引き継ぐ案。
名前の選択保持は今回の合意に従い、localStorage のメンバー ID を使う。
初回や保存済み ID が無効な場合は、先頭メンバーを自動選択せず明示選択を求める案。

保存先がダイアログではなく独立画面になるので、成功時は画面を閉じず、保存完了を表示する案。
保存済みの基準値を更新し、再集計結果を取得する。取得失敗は保存失敗とは区別する。
集計の表示は保存済み回答に基づくと分かるようにし、下書きを混ぜて確定人数として扱わない。
保存中は名前の選択も含めて変更できないようにし、保存対象と表示対象の混同を防ぐ。
画面内の再読み込みと他メンバーへの変更でも、未保存データを確認なしに破棄しない。
名前の保持以外に未保存の回答データをブラウザーへ永続保存することは、初期案に含めない。

これらの Web版固有の挙動は設計案であり、現行と異なる点を実装前に確認する。

## 提供された CandidateDialog HTML から確認した仕様

### 目的

参加者が回答する候補日時の一覧を編集する画面。
通常の時間枠とは別に対象週の日時を追加したり、不要な候補を削除したりする。
この HTML は開催日時を確定する操作を提供していない。
確定日時の選択は、現行では「開催日程」B3 の選択欄が担当する。

### 画面の操作

- 初回に `getCandidateData` で対象週と登録済み候補を取得する。
- 候補日の初期値は週開始日、時刻の初期値は21:30。
- 日付と30分刻みの時刻を指定し、`addCandidate` を呼ぶ。
- 削除は確認を表示してから `removeCandidate` を呼ぶ。
- 成功時はサーバーが返した候補一覧で画面を更新する。失敗時はエラーを表示する。
- 一覧はサーバーから返された順のまま表示し、この HTML では日時順に並べ替えていない。
- 重複、週の範囲、回答済み候補の削除禁止はスクリプト側が検証する。
- 候補の日付や時刻をその場で編集する機能はない。
- この HTML 内に管理者ログインや権限検証はない。

### Web版への反映案

管理者画面の「回答対象日時の調整」という補助操作にまとめ、参加者には表示しない案。
普段は週の標準時間枠を使い、必要な週だけ日時を追加・削除できるようにする。
追加・削除の権限は画面とバックエンドの両方で制御する。
回答済み候補は削除しないという現行ルールを引き継ぐ案。
削除可能かの確認と削除は原子的に行い、確認後に回答が入った場合も保護する。

現行の週更新は手動追加候補も7日進めて引き継ぐため、
Web版でも追加候補を翌週へ引き継ぐことが今回の確定要件となった。
候補一覧は日時順に表示し、追加・削除中は入力と操作を無効化する案。
